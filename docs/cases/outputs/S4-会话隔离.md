# S4 执行记录 — 批量会话不许碰浏览器，人工会话不受影响

> 目的：验证 `sessions.allowlist` 是**按会话**生效的隔离，而不是一刀切。
> 执行时间：2026-11-22 12:1x（北京时间）。环境：DSH 0.2.2-rc.5 · agent-browser 1.4.3 · GUI 127.0.0.1:9529。
> 案例来源：`docs/cases/014-practical-cases.md` §3 S4。判定：L3（两个会话行为不同 + 恢复默认）。

## 0. 结论

- **L3 达成**：把 allowlist 设为「当前人工会话」后，本会话的 `browser_open` 正常；另起的一次性子代理（不同 session）调用同一工具被 `session_not_allowed` 拦下。删除配置后恢复默认（空名单 = 全放行）。
- 这条同时验证了「人机并存」的默认部署姿势：允许人用浏览器，把自动化会话写进名单外。

## 1. 配置（临时，已删除）

```yaml
- id: agent-browser-panel
  config:
    sessions:
      allowlist:
        - session-bb049fec-f7f6-4546-92ec-64eafd80156c
```

## 2. 证据

| # | 会话 | 动作 | 结果 |
|---|---|---|---|
| 1 | 本会话（人工）`session-bb049fec-…` | `browser_open https://example.com/` | `Opened https://example.com/ — Example Domain` ✅ 放行 |
| 2 | 子代理会话（自动化，独立 session） | `browser_open https://example.com/`（同一参数） | `Error: session_not_allowed: this session is not allowed to drive the browser (session_not_allowed)` ✅ 拦截 |
| 3 | 清除配置并重载后 | 子代理再调一次 | 见 §3 恢复验证 |

> 子代理是真实独立会话（`subagent` 起的一次性 agent），同一条 `browser_open` 命令在两个会话里得到相反结果——这就是"按会话隔离"的直接证据，而不是靠改参数自证。

## 3. 恢复验证（清空配置后）

- 清除 profile 临时块（文件回到 2,071 字符 / 54 行）并重载（桥端口 2067 → 7627）。
- 子代理再次调用 `browser_open https://example.com/`：**不再报 `session_not_allowed`**（拦截已解除），改报
  `Error: panel_not_open: the browser panel of session cbb666f0… is not on screen, so the page cannot be driven. Open that session and its right sidebar browser tab, then retry.`
  —— 这是子代理会话没有打开面板的**环境语义**，与策略无关；说明名单清除后 guard 已放行（见 §4 第 2 条）。
- 本会话工具同步正常（同一次重载后 `browser_open` 通过）。

## 4. 观察

1. 名单是**精确字符串匹配**（本会话 id 必须逐字一致；写错一个字符即拦截）。
2. 拦截发生在 `ctx.tools.guard()`（工具体之前），所以被拦时不会有命令进入桥、也不会动面板——这与 H4 的证据一致。
3. 文档口径：用户 README「工具报 `session_not_allowed`」行 → 把当前会话 id 加进名单或清空名单；实操与文档一致。
