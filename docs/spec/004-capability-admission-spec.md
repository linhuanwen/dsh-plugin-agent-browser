## 1. 目的

产品定位是「用户和 agent 共用一块真浏览器」（SPEC-001 §2）。这个定位的护城河是**可见、可接管、登录态零搬运、失败可核对**，而不是能力数量——调研报告已判定：能力宽度永远追不上 CDP 派（BrowserSkill 的 11 域工具 + 1298 个测试、browserpaw 的 92 条命令、browser-cdp 的 35 个工具，都是靠「另养一只浏览器」换来的）。

1.5.2 已经立起第一道信任闸门（SPEC-003：站点级首次写动作确认）并真机验收。接下来的问题是**怎么长大而不把信任弄丢**。

本规格要冻结的规则只有一句：

> **先立规矩，让规矩成为扩功能的门禁：任何新能力都必须先通过「准入四问」，再交付「证据四件套」，才能进主干。**

「边界」不是一批做完就不再变的功能，而是每加一个能力都要重新回答的四个问题；因此本规格把边界冻结为**契约**（§4 B1–B3），把「边界收口」冻结为**阶段 A 的有限清单**（§6），把功能扩展冻结为**阶段 B 的三层顺序**（§6）。这样既不失去纪律，也不会因为「边界永远做不完」而卡死。

## 2. 非目标

| 不做 | 原因 |
|---|---|
| 用竞品功能清单当路线图 | 35/43/92 个工具是通用市场解法；追它会稀释「共用一块真浏览器」的定位（调研报告 §5） |
| headless / 远程 / 多后端 / CDP 第二后端 | 产品路线已判定不做（决策 005、006；调研报告 §7） |
| 跨 harness 的 CLI / MCP 发行 | 会让宿主 UI、策略、下载、审批、错误码全部脱钩（调研报告 §2.1） |
| 站点专用「配方」工具（知乎/小红书/抖音…） | 维护成本高、易随站点改版失效；需要时用 `browser_eval` + 通用工具组合 |
| 把审批做成通用工作流引擎 | 审批只回答「这一次写动作发不发」，不做多步编排（SPEC-003 §2 边界不动） |
| 阶段 A 顺手加新动作 | 阶段 A 只收口，不加读/写动词；新动词一律进阶段 B 的批次 |

## 3. 术语

- **读动作**：不产生页面副作用、不需要确认的动作。现有：`browser_open`（导航）、`browser_snapshot`、`browser_scroll`、`browser_hover`、`browser_zoom`、`browser_screenshot`、`browser_press` 中的非提交键。
- **写动作**：会改变页面状态或对外产生副作用的动作。现有四类 `actionClass`：`type` / `submit` / `download` / `eval`（SPEC-003 §4 C2）。
- **不可逆动作**：写动作中「发出后无法撤回」的子集，例如提交表单、下载落盘、`eval` 造成的服务端副作用。写 ≠ 不可逆：**键入可撤销，提交不可撤销**。
- **准入四问**：①读还是写 ②可逆吗 ③失败能否确定「未执行」 ④人机墙/接管时能否被正确拦住（见 §4 B1）。
- **证据四件套**：单测、至少一条真机 case、错误码与 hint、文档三处同步（见 §4 B3）。
- **边界收口**：阶段 A，把「行为边界」的已知缺口补到可验收，见 §6。
- **能力扩展**：阶段 B，在契约内新增浏览器能力，按 §6 三层顺序推进。

## 4. 要求

### B1 准入四问（每个新增能力必须有书面答案）

任何新增工具、任何新增动作类型、任何新增命令帧，必须先在对应 ticket 里回答：

| # | 问题 | 不回答的后果 |
|---|---|---|
| 1 | 它是读还是写？写的话属于哪个 `actionClass`？ | 审批分类错，用户对「agent 能做什么」失去预期 |
| 2 | 它可逆吗？不可逆是否需要在结果里显式标注？ | 用户无法判断「这次要不要拦」 |
| 3 | 失败时能不能确定「动作没有发出」？不确定时是否 fail-closed？ | 会出现「说失败其实成功」的幽灵动作（与 SPEC-003 C5 同源） |
| 4 | `needs_human` / `taken_over` 相位下它会不会绕过门？ | 会出现「验证墙上 agent 还在动」（验收期真实发生过，TICKET-037 修） |

**判定规则**：四问中任一问答不上来 → 该能力**不进主干**；只能作为实验分支存在，并且默认关闭（`mode:'off'` 等价物）。

### B2 能力分类与默认行为

| 类别 | 例子 | 默认行为 | 失败语义 |
|---|---|---|---|
| 读 | snapshot / scroll / hover / zoom / screenshot | 零确认，随时可打断 | 可重试 |
| 可逆写 | type（键入） | 站点首次写动作确认 | 可重试，但**先重读再决定** |
| 不可逆写 | 提交、下载、eval | 同上，且结果必须带「不可逆」标记 | 未知态绝不自动重放 |
| 高风险读（新增） | console / network 观测 | 零确认，但要能整体关闭 | 可重试 |

新类别（例如上传、拖拽、多标签切换）必须先在 ticket 里给出「为什么它属于这一类」的论证，再进 §6 批次。

### B3 证据四件套（缺一不进主干）

1. **单测**：新增纯逻辑要有独立 `.test.mjs`；碰 bridge 协议要有 bridge 流测试；页面注入逻辑要能像 `detect.test.mjs` 那样用 stub DOM 跑。
2. **真机 case**：至少一条在真实 DSH 面板上的验收记录，写进 `docs/cases/`（编号续 016 起），并注明宿主版本与插件版本。
3. **错误码与 hint**：新失败模式要么复用既有码（1.5.8 起 19 个：1.5.4 的 `action_unknown`、`stale_cursor`、`upload_rejected`），要么新增码并同时更新 `plugin/errors.js`、用户 README 故障排查表、SPEC-003 的码表表述（check-docs 会校验部分）。
4. **文档三处同步**：用户 README（工具表 / 配置表 / 已知限制）、`docs/README.md` 索引、`PROGRESS.md` 的目录树与「下一步」；新增配置字段还要同步 `plugin/config.js`、`plugin/index.js`、`dist/.../README.md`（check-docs 的三处校验）。

### B4 失败语义：写动作必须能回答「未执行 / 已执行 / 未知」

所有写动作的结果必须能归入三态之一，并且**未知态不得自动重放**：

| 态 | 含义 | 允许的后续 |
|---|---|---|
| `none` | 校验失败或未发出（审批拒绝/超时/不可见、参数不合法） | 修正参数后重试 |
| `committed` | 页面确认动作已执行 | 不再重放；需要时重读页面核对 |
| `unknown` | 已交给页面但回执丢失（超时/通道断开） | 只允许 `browser_snapshot` 等读动作核对，禁止自动重发 |

实现见 TICKET-042（2026-11-26 已落地，单测 `plugin/test/effect.test.mjs`）：为写工具回执加 `effect` 字段，并新增 `action_unknown` 错误码（`retryable:false`，hint「先 snapshot 核对，不要重发」）。**该条落地后，新增不可逆写动作才可通过 B1 准入**。

### B5 人工优先级不变

`needs_human` / `taken_over` 相位 > 审批 > 执行。任何新能力必须显式通过 `READ_TYPES` / `INPUT_TYPES` 门，读命令不得把相位抢回 `agent`（TICKET-037 的教训）。新增能力若需要新帧类型，帧类型必须归入「读」或「写」两桶之一，不允许「既不清相位也不走门」的第三种。

### B6 反回归门禁

每次发版前固定跑：

1. `node --test plugin/test/*.test.mjs` 全绿（当前 251 例，只增不减）；
2. `node tools/check-docs.mjs` 六项全绿；
3. `node tools/pack.mjs` 后 dist↔plugin 源文件 SHA256 一致、`files` 白名单包含新文件；
4. 至少一条与改动相关的真机 case 记录（阶段 A 期间用 `docs/cases/015` §4 的格式续写）。

### B7 明确不做清单（与调研报告 §7 一致）

headless、远程控制、多浏览器后端、CDP 第二后端、跨 harness CLI/MCP、站点专用工具、无头 Playwright、把下载/上传拆成独立进程、把审批做成工作流引擎。**新增一条不做，必须有新的书面理由**，不能因为「竞品有」就加。

### B8 两步走

- **阶段 A（边界收口，v1.5.x）**：只做 TICKET-040–043，不加新动词。
- **阶段 B（能力扩展，v1.6+）**：按 §6 三层顺序推进，每层每个能力过 §4 B1–B4。

## 5. 兼容性

1. **工具名不变**：阶段 A 期间工具表仍是 11 个；阶段 B 新增动词只加不改（`browser_*` 命名不变），既有参数语义不变。
2. **配置向后兼容**：新增配置字段一律有默认值；`approvals.mode:'off'` 必须保持 1.4.x 行为（SPEC-003 C12）。
3. **错误码只增不改**：新码必须 `retryable` 显式声明；既有 16 码的语义不动（1.5.4 新增 `action_unknown` = 第 17 码）。
4. **宿主版本窗口不变**：`engines.dsh >=0.2.2-rc.3 <0.3.0`。
5. **CLIENT_REV**：任何 `plugin/client.js` 行为变化都要 bump，并在 PROGRESS 开发循环第 8 条里记录。

## 6. 批次与顺序

### 阶段 A：边界收口（先做完这四件，再谈扩展）

| 顺序 | ticket | 内容 | 出口条件 |
|---|---|---|---|
| A1 | TICKET-040 | DSH 白屏/重启根因：客户端重载后整树白（两次实时发生，无 crash 日志） | 能稳定复现或给出「不可复现 + 加固措施」，并把真机验收流程改为不依赖热重载 |
| A2 | TICKET-041 | JS 弹窗（`alert/confirm/prompt/beforeunload`）卡死页面：全仓无任何处理 | 弹窗出现时工具不挂死，agent 能看见、能处置，用户能接管 |
| A3 | TICKET-042 | 写动作回执三态 `effect` + `action_unknown` | 写工具回执带 effect；未知态测试证明不重放；错误码表 16→17 |
| A4 | TICKET-043 | F7（`sensitiveSites` 每次必问）/ F8（`mode:'off'`）安全真机验收 | 不做热重载：重启后一次注入配置；F7/F8 有真机记录或明确降级说明 |

**阶段 A 的硬约束**：期间若再发生白屏，暂停一切真机验收，只做代码与文档，直到 A1 有结论。

### 阶段 B：能力扩展（按层推进，不跨层跳）

| 层 | 能力（按优先级） | 为什么在这个层级 |
|---|---|---|
| B1 操作补全 | `browser_wait`（等待条件）、标签页（list/switch/close）、上传（fileChooser）、拖拽、滚动到元素 | 都是「做完一件事」需要的动作，风险可控；上传/拖拽必须先过准入四问 |
| B2 观察增强 | console / network 观测、快照语义（遮挡提示、`[ctx:]`、token 预算 + cursor）、`loc=` 稳定定位 | 让 agent 判断更准，不增加写风险；`loc=` 要处理「跨快照稳定性」 |
| B3 高风险 | iframe 直连（`webContents.mainFrame.frames` 探针）、带 Cookie 的下载通道、取消传播、多标签并行 | 都触及宿主/Electron 边界或会放大副作用，必须单独规格 + 用户可见的关闭开关 |

**Stage B 的前置条件**：阶段 A 四个 ticket 全部结案；SPEC-004 的 B1–B4 在至少两个真实能力上走通（证明契约可用）。

## 9. 风险

| # | 风险 | 缓解 |
|---|---|---|
| R1 | 契约写得太重，拖慢扩展 | 证据四件套尽量复用既有测试骨架，不新造流程；阶段 B 每层先做一个能力试点 |
| R2 | 弹窗处理改变页面语义，站点检测到被 hook | 默认「记录 + 拦截」，不做静默放行；`mode:'off'` 可回到原语义 |
| R3 | 白屏不可复现，A1 无限期挂起 | 给 A1 设时限；超时则改为「规避 + 加固」结案（禁用热重载验收、改重启注入） |
| R4 | `effect` 三态让 agent 过度保守 | hint 里写清「unknown 只读核对」，并在 docs 里给出示例 |
| R5 | 阶段 B 能力互相依赖（如标签页 + 快照 scope） | 每层先定顺序，后置能力不得反向要求前置能力改语义 |

## 10. 与上一版关系

- 不改 SPEC-001（产品范围与 A1–A19）、SPEC-002（工程约束 B1–B11）、SPEC-003（审批契约 C1–C12）的任何条款，只在其上追加「新增能力的审批规则」。
- 本规格吸收调研报告 §5–§6 的结论与 2026-11-26 的产品讨论（先边界后能力、边界即门禁）。
- 与 SPEC-003 的关系：SPEC-003 是「第一次写动作怎么问」，本规格是「以后每加一个能力怎么不破坏这个问法」。
